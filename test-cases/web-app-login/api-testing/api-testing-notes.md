# API Testing Notes – REST API (Pet Project)

## Общая информация

- **Проект:** Web Application (учебный pet-проект)
- **Модуль:** REST API (авторизация, пользователи, заказы)
- **Дата:** 01.08.2026
- **Автор:** SharLodka
- **Инструменты:** Postman, Chrome DevTools (Network), JSON

## Описание API

Базовый URL:  
`https://example-app.com/api`

Основные эндпоинты, которые тестировались:

- `POST /auth/login` – авторизация пользователя
- `GET /users/{id}` – получение данных пользователя
- `GET /orders` – получение списка заказов
- `POST /orders` – создание нового заказа

## Сценарии тестирования

### 1. Авторизация (POST /auth/login)

**Цель:** Проверить, что API корректно обрабатывает запросы на логин.

**Запрос:**

- Method: `POST`
- URL: `https://example-app.com/api/auth/login`
- Headers:
  - `Content-Type: application/json`
- Body (JSON):

```json
{
  "email": "user@example.com",
  "password": "Test1234!"
}
```

**Ожидаемый результат (успешный логин):**

- Статус: `200 OK`
- Response body содержит:
  - `token` (JWT или иной токен доступа)
  - `user_id`
  - `email`

**Пример ответа:**

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user_id": 123,
  "email": "user@example.com"
}
```

**Проверки:**

- Статус-код = 200
- В ответе есть поле `token`
- Тип токена – строка, не пустая
- `user_id` соответствует переданному пользователю

---

### 2. Неверный пароль (POST /auth/login)

**Запрос:** как выше, но `password` неверный.

**Ожидаемый результат:**

- Статус: `401 Unauthorized`
- Response body содержит сообщение об ошибке, например:

```json
{
  "error": "Invalid email or password"
}
```

**Проверки:**

- Статус-код = 401
- В ответе есть поле `error`
- Сообщение понятное, без утечки чувствительных данных

---

### 3. Получение данных пользователя (GET /users/{id})

**Запрос:**

- Method: `GET`
- URL: `https://example-app.com/api/users/123`
- Headers:
  - `Authorization: Bearer <token>`

**Ожидаемый результат:**

- Статус: `200 OK`
- Response body содержит:
  - `id`
  - `email`
  - `name`
  - другие поля профиля

**Проверки:**

- Статус-код = 200
- `id` в ответе совпадает с `{id}` в URL
- Нет лишних чувствительных данных (пароли, хеши и т.п.)

---

### 4. Создание заказа без авторизации (POST /orders)

**Запрос:**

- Method: `POST`
- URL: `https://example-app.com/api/orders`
- Headers:
  - `Content-Type: application/json`
  - **без** `Authorization`

**Ожидаемый результат:**

- Статус: `401 Unauthorized` или `403 Forbidden`
- В ответе сообщение, что требуется авторизация.

**Проверки:**

- Статус-код = 401/403
- В ответе есть понятное сообщение об ошибке

---

### 5. Создание заказа с авторизацией (POST /orders)

**Запрос:**

- Method: `POST`
- URL: `https://example-app.com/api/orders`
- Headers:
  - `Content-Type: application/json`
  - `Authorization: Bearer <token>`
- Body (JSON):

```json
{
  "items": [
    {
      "product_id": 10,
      "quantity": 2
    }
  ],
  "address": "Kazan, st. Example, 1"
}
```

**Ожидаемый результат:**

- Статус: `201 Created`
- Response body содержит:
  - `order_id`
  - `status` (например, `new` или `pending`)
  - `items`
  - `address`

**Проверки:**

- Статус-код = 201
- В ответе есть `order_id`
- `items` и `address` совпадают с отправленными
- `status` имеет допустимое значение

---

## Что проверялось

- Корректность статус-кодов (200, 201, 400, 401, 403, 404, 500).
- Структура JSON-ответов (наличие обязательных полей).
- Обработка некорректных данных (неверный пароль, пустые поля).
- Поведение API без токена авторизации.
- Базовая валидация входных данных.

## Как использовалось

- Коллекция запросов оформлена в Postman и экспортирована в файл:  
  `api-testing/postman-collection.json`
- Для каждого сценария в Postman заведены:
  - запросы;
  - примеры ответов;
  - простые тесты (статус-код, наличие полей).
